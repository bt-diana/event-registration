# Spec: Outbox sender (real email through Resend, with retries) and reminder worker (M6, API only)

Feature spec for milestone M6, made from `SPEC_TEMPLATE.md` (sections 1-5). Roadmap steps 29-32 (this spec is step 29); behaviour B5. One small migration (`004_outbox_status.sql`) adds a delivery status to `outbox`; everything else about the table (`kind` CHECK, `sent_at`, `UNIQUE (registration_id, kind, schedule_version)`) stays as in `DATABASE.md` (section 1, 3.2, decisions 5, 6 and 13). Outbox rows of kind `ticket` are already written by `api/src/registrations/service.ts` (`registration.md`); `promotion` rows come with M4. Reschedule and event-cancel emails (rows of kind `reschedule` and `event_cancelled`, B8, B9) are M7 and extend this file later. The UI side (step 33) is `email-reminders-web.md`. Ids are ER1, ER2, ... (ids ER1-ER38 keep their numbers from the previous version of this spec; ER7 and the wording of the sender rows changed; ER39-ER47 are new).

**Decisions that shape this version.** D52 (checked-in people get no reminder, send before commit = at least once, period 10 s, reminder text, queued reminders stay for M7) still holds. D56: a failed send is tried at most 3 times in total, then the row gets the status `error_sending` and is never selected again. **D58** (replaces D57 and the "fetch, no library" part of D53): real sending is in scope, through the `resend` npm package (a new dependency in `api/`, approved by the user). **D59**: the API refuses to start when `EMAIL_API_KEY` or `MAIL_FROM` is missing or blank.

**What the Resend docs show** (read on 2026-10-18; the code-writer re-checks the types after `npm install`, see "Verify at install" in section 3):
- Send: `import { Resend } from 'resend'; const resend = new Resend(apiKey); const { data, error } = await resend.emails.send({ from, to: [address], subject, text })` (https://resend.com/docs/send-with-nodejs).
- **The SDK does not throw on API errors.** It returns `{ data, error }`: on success `data.id` is set and `error` is `null`; on failure `data` is `null` and `error` has `name` and `message` (same page). The page says `try/catch` is only for network-level failures. So the wrapper must check `error` and throw (ER40) or a 403 or a 429 would count as a success. A timed-out or aborted request is reported with `statusCode` `null` (https://github.com/resend/resend-node); the wrapper handles both a returned `error` and a rejected promise (ER41).
- **Idempotency:** the Node option is `idempotencyKey` (https://resend.com/docs/dashboard/emails/idempotency-keys). Key: 1 to 256 characters, kept 24 hours. Same key and same payload within 24 hours: Resend returns the original response and does not send again. Same key and a different payload: `409 invalid_idempotent_request`. Same key while the first request is still running: `409 concurrent_idempotent_requests`. The changelog (https://www.resend.com/changelog/idempotency-keys) shows the key as an option in a **second argument** of `emails.send(payload, { idempotencyKey })`; the Node page example is not clear about the place. See "Verify at install".
- **Errors that matter** (https://resend.com/docs/api-reference/errors): `429` `rate_limit_exceeded` (default 10 requests per second per team), `429` `daily_quota_exceeded` and `monthly_quota_exceeded`, `500` `application_error`, `503` `service_unavailable`, `403` `validation_error` for "you can only send testing emails to your own email address" (no verified domain) and for a `from` domain that is not verified, `401` `validation_error` or `missing_api_key` for a bad key.
- **Timeout:** the SDK has no timeout option of its own. Request options take a `signal`, so `AbortSignal.timeout(ms)` works on Node 18+ (https://github.com/resend/resend-node; the exact place is again checked at install). `resend` 6.34.1 (npm, current) needs Node `>=20`; its own dependencies are `postal-mime` and `standardwebhooks`.

## 1. Goals and expected behaviour

**Goal.** Every email that the app decides to send is a row in `outbox`. A sender takes each `pending` row, sends it through an `EmailTransport` (a function; in production the Resend one), and sets `status = 'sent'` and `sent_at`. If the transport rejects, the row is tried again on the next timer tick, at most 3 tries in total; after the third failure it becomes `error_sending` and stays out of the queue. A reminder worker writes one `reminder` row for each seated person in the 24 hours before the event, once per schedule version, even if the worker runs many times or in parallel. A timer starts both. The API does not start without `EMAIL_API_KEY` and `MAIL_FROM` (D59).

**Delivery guarantee (at least once).** The provider call cannot be inside the database transaction in a way that makes it undoable: if the provider accepted the email and the process dies before the `COMMIT`, the row is still `pending` and the next run sends it again. The opposite order (mark first, send after) would lose an email when the send fails. D52 answer 2 stands: **a row is never lost; in a rare crash, or when a call timed out after the provider had already accepted it, the email can be sent twice.** Two things reduce this: each row is claimed, sent and marked in its own short transaction (only one email is at risk), and the sender passes the **outbox row id as the idempotency key** (ER4), so a repeat of the same row within 24 hours with the same text is answered by Resend with the original result and not sent again. The guarantee for the app stays "at least once"; the key makes a duplicate unlikely, not impossible (a key older than 24 hours, a crash after a changed row text, a provider outage on the repeat).

**Failure and retry (D56).**
- A try is one call of the transport for one row. A try fails when the transport throws or its promise rejects. For the Resend transport that includes a returned `error` (ER40), a network error, a timeout (ER43), a `429` and a `5xx`. All of them are failed tries like any other and count toward the 3; there is no special case and no back-off.
- `send_attempts` counts failed tries. A failed try does `send_attempts + 1` and stores a short reason in `send_error`. On the third failed try (`send_attempts` reaches 3) the status becomes `error_sending`. Otherwise the row stays `pending`.
- A row that failed in a round is not tried again in the same round (it would only fail again): the retry is on the next timer tick. So the 3 tries take at least two ticks (about 20 s with the 10 s period).
- `error_sending` rows are never selected again and are **not retried automatically**. A manual re-queue (a route, a script, a button) is out of scope.
- **Free-tier limit.** Without a verified domain Resend delivers only to the address of the account owner (403). Every other address ends as `error_sending` after 3 tries. This is expected in development and is written in the README.
- The reminder worker's unique key still blocks a second reminder for the same person and schedule version, even when the first one is `error_sending` (ER31). A new schedule version (M7) gives a new row, as before.
- **Why the counter survives.** The failed try is not rolled back. The claim transaction holds the row lock; on failure it runs `UPDATE ... SET send_attempts = send_attempts + 1, send_error = ..., status = ...` and **commits**. So the increment is persisted, and because the lock is held until that commit, a parallel sender (which uses `SKIP LOCKED`) can neither pick the row nor count the same try twice. Only a crash or a database error between the send and the commit leaves the count unchanged (that try is not counted, consistent with at least once).
- **Lock and connection during the HTTP call.** The row lock and one pool connection are held while the provider call runs. So the transport must always end: the Resend transport has a timeout (default 10 s, ER43). The SDK has no timeout option of its own; the wrapper passes `AbortSignal.timeout(ms)` as the request `signal` and, as a second guard, races the call against a timer (so a client that ignores the signal cannot hold the lock). A timed-out call is a failed try.

**Privacy.** The email address and the body (it holds the ticket code) are personal data. The sender never logs them: the success line has the kind and the row id only (ER7), failed tries log a reason without address or body (ER17), and the API key is never logged or put in an error message (ER40, ER46). The old development line with the body (`c36c710`) is dropped: with real delivery the mailbox is the place to read the email, and a log with ticket codes and addresses is a leak with no use left.

**Behaviours.** Each line is something a test can prove. "Yes" means the test is written and committed before the code (red). Tests never send real email: no test reads `EMAIL_API_KEY`, none builds `new Resend(...)`, the transport is always a fake function or a wrapper around a fake client object.

**No HTTP route.** Nothing is triggered over HTTP, so `api/openapi.yaml` does not change. A partial index on `status = 'pending'` is not added (small tables; add it when a measurement says so). `setInterval` from Node is the timer. The one new library is `resend` (D58).

**Not in this spec.** HTML emails (the email is plain `text`), bounce and complaint handling, unsubscribe links, delivery webhooks and delivery status (`sent` means "the provider accepted it", not "it arrived"), a manual or automatic re-queue of `error_sending` rows (and any route, screen or script that lists them), back-off between tries, a configurable retry count, a send-rate limiter, other providers and a provider setting, a verified domain or DNS set-up, a fake mail server, per-user reminder settings, a reminder for waiting people (`DATABASE.md` decision 6), a second reminder at another time, reschedule and event-cancel emails and their rows (M7, B8, B9; the sender sends such rows exactly like the others, ER9), promotion rows (M4), removing an already queued reminder when the event is rescheduled or cancelled or the person cancels afterwards (the row is an email that is already queued and the sender sends it), the web notes (step 33).

**Assumptions.** Change any of these first in this file.
- A row is "sent" when the transport resolved and the row's transaction committed. At least once, as described above.
- The sender claims one row at a time in its own transaction, on one pool client: `BEGIN`; `SELECT id, kind, to_email, subject, body FROM outbox WHERE status = 'pending' AND id <> ALL($1::uuid[]) ORDER BY created_at, id LIMIT 1 FOR UPDATE SKIP LOCKED` (`$1` = ids that already failed in this call); `await transport(...)`; then on success `UPDATE outbox SET status = 'sent', sent_at = now(), send_error = NULL WHERE id = $2`, on failure `UPDATE outbox SET send_attempts = send_attempts + 1, send_error = $3, status = CASE WHEN send_attempts + 1 >= 3 THEN 'error_sending' ELSE 'pending' END WHERE id = $2`; `COMMIT` in both cases; repeat up to `batchSize` tries. If a database statement fails: `ROLLBACK`, release the client, rethrow. `onError` and `log` are called after the commit. `SKIP LOCKED` makes a second sender take other rows or none, never the same row. `sent_at` uses the database clock; only the reminder window uses the injected clock. The limit 3 is one constant (`MAX_SEND_ATTEMPTS`), not an option or a setting.
- `send_attempts` means failed tries. A row that was sent after two failures has `send_attempts = 2`. Rows backfilled as `sent` keep 0.
- `send_error` is an optional column, the reason of the last failed try: a short message only (at most 200 characters, addresses replaced), never the body. Why a column at all: without it the only trace of why a row is `error_sending` is a console line that is gone after a restart, and a later step (manual re-queue, an admin view) needs to tell the rows apart. It is NULL for rows that never failed and is cleared when a retry succeeds. It is written only by the sender.
- Sending is one row at a time, so one sender cannot make more than a few calls per second; the default `batchSize` of 5 per 10 s tick keeps one API process far below Resend's default limit of 10 requests per second. A longer worst case is accepted: a round with 5 rows and a provider that hangs lasts up to 5 x 10 s; the runner skips the firings in between (ER34).
- A row that always fails leaves the queue after 3 ticks (about 20 s with the 10 s period), so it can delay newer rows by at most 3 ticks (ER16).
- One reminder per registration per schedule version, so a person who cancels and registers again (a new registration row) can get a new reminder. A checked-in person gets none (ER23).
- A person who registers inside the 24-hour window gets their ticket email and, at the next round, a reminder too. No special case.
- Time in the body is UTC, like the ticket email. No time-zone handling.
- The email address is personal data: it is stored in `outbox` and sent to the provider, nowhere else (not in logs, `onError` messages or `send_error`, ER7, ER17).
- `MAIL_FROM` is passed as the `from` string unchanged (`onboarding@resend.dev` or `Name <address>`); the app does not check its format, the provider does.
- Tests use a test schema (`createTestDb()` from `api/test/db/helpers.ts`) and insert rows by SQL with the helpers there (`insertEvent` takes `startsAt`, so events are placed relative to the fake clock). The existing `api/test/db/reminder.test.ts` proves the unique key and the `schedule_version` loop with its own copy of the statement; it stays. The new tests call the real `enqueueReminders`. A cleanup of `outbox` rows by a test follows the rule in `checkin.md` (outbox first). No test needs environment settings except `DATABASE_URL`, and no test reads `EMAIL_API_KEY`.
- The default period of 10 s is for a demo; reminders are daily, so any period up to a minute is fine.

## 2. UI decisions

No screen in this spec (API only, no new route). What the web can show about emails (step 33, `email-reminders-web.md`) can use only data that already exists. Nothing here changes a response shape: `status`, `send_attempts` and `send_error` are not returned by any route. The web must not say that an email "arrived": `sent` only means the provider accepted it. Note for step 33: that spec still says the stub prints `[email] ...` lines with the content (its W-EM2 and its remark on ER7); with this version the console line holds no content and the email goes to the mailbox, so that spec needs a small update.

## 3. Architecture decisions

- **Apps:** `api/` only. Express 5, TypeScript, Vitest, `pg`, and now `resend`. One migration, one new dependency, no HTTP route. Env variables: `EMAIL_API_KEY` and `MAIL_FROM` (required, D59), `EMAIL_JOB_INTERVAL_MS` (optional).
- **Migration `004_outbox_status.sql`** (next number after `003_event_description.sql`; same style as `002` and `003`: a header comment that names this spec and `DATABASE.md`, `001` to `003` are not edited):
  ```sql
  ALTER TABLE outbox
    ADD COLUMN status text NOT NULL DEFAULT 'pending'
      CHECK (status IN ('pending','sent','error_sending')),
    ADD COLUMN send_attempts integer NOT NULL DEFAULT 0 CHECK (send_attempts >= 0),
    ADD COLUMN send_error text;
  UPDATE outbox SET status = 'sent' WHERE sent_at IS NOT NULL;
  ALTER TABLE outbox
    ADD CONSTRAINT outbox_status_sent_at CHECK ((status = 'sent') = (sent_at IS NOT NULL));
  ```
  The backfill runs before the consistency CHECK is added, so existing rows pass it. The CHECK on `status` and the one between `status` and `sent_at` are the whole schema guarantee; `3 tries` is app logic, not schema (no CHECK on `send_attempts` against 3). The unique key is untouched. `sent_at` stays: it records when, `status` records what.
- **Rows written by other code:** `registrations/service.ts` (and the cancel and promote code) insert `outbox` rows with named columns and none of the new ones, so they get `pending`, 0, NULL by the defaults. No change there (ER3).
- **Files (new folder `api/src/email/`):**
  - `transport.ts`: the `EmailTransport` type and `createResendTransport` (ER39-ER43). It is the only file that imports `resend`. The Resend client is typed by a small structural interface (`{ emails: { send(payload, options?): Promise<{ data, error }> } }`) so a test passes a plain object.
  - `config.ts`: `readMailConfig(env)` (ER44-ER46).
  - `sender.ts`: `formatSentLine(row)`, `MAX_SEND_ATTEMPTS = 3` and `sendPending(pool, options)`; no timer, no HTTP, no import of `resend`.
  - `reminders.ts`: `enqueueReminders(pool, now)`; no timer.
  - `runner.ts`: `createRunner(task, { intervalMs, onError })` returns `{ stop }`; generic, no database, so the timer behaviour (ER33-ER36) is tested with fake timers and a task the test controls.
  - `jobs.ts`: `readIntervalMs(env)` and `startEmailJobs(options)`; composes the worker, the sender and the runner (ER32, ER37).
- **Transport design (D58).** `EmailTransport` is a plain function type, so the sender depends on it and not on Resend. `createResendTransport` is a thin wrapper: build the payload, call `client.emails.send`, turn `{ error }` into a thrown `Error` (the SDK does not throw), apply the timeout, return nothing. It does not retry, log or clean addresses. Production wiring is in `index.ts` only: `createResendTransport(readMailConfig(process.env))`.
- **Sender (ER4-ER17), concurrency and delivery:** as in the Assumptions. One transaction per row. The transport is awaited, so a test can hold a try open with a promise. The same client does the claim, the send and the final `UPDATE`, which is why the failure counter is committed with the lock still held (no lost increment, no double count). The failed ids list keeps a row out of the rest of the call. A pool client is used for one row at a time, so a sender never needs more than one connection; the lock and the connection are held during the HTTP call and bounded by the transport timeout (ER43). With `pg`'s default pool size (10) and the few senders this app runs, that is fine; the timeout is what makes it safe.
- **Reminder worker (ER18-ER31): one statement, no transaction needed.** `$1` is the injected `now`:
  ```sql
  INSERT INTO outbox (registration_id, kind, schedule_version, event_starts_at, to_email, subject, body)
  SELECT r.id, 'reminder', e.schedule_version, e.starts_at, u.email,
         'Reminder: ' || e.title || ' starts soon',
         e.title || E'\n' || 'Starts: ' || to_char(e.starts_at AT TIME ZONE 'UTC', 'YYYY-MM-DD HH24:MI') || ' (UTC)'
           || E'\n' || 'Ticket code: ' || r.ticket_code
    FROM registrations r
    JOIN events e ON e.id = r.event_id
    JOIN users u ON u.id = r.user_id
   WHERE r.status = 'registered' AND r.checked_in_at IS NULL
     AND e.status = 'active'
     AND e.starts_at - interval '24 hours' <= $1::timestamptz
     AND $1::timestamptz < e.starts_at
  ON CONFLICT (registration_id, kind, schedule_version) DO NOTHING;
  ```
  The unique key is the whole "once" rule (`DATABASE.md` 3.2): it counts rows of every status, so an `error_sending` or `sent` reminder blocks a new one for the same person and version (ER31). Nothing depends on timing or on a lock in the app. Under READ COMMITTED a parallel second statement waits for the first one's uncommitted rows on the unique index, then does nothing. `rowCount` is the number inserted. The statement is not limited to one event, so it handles every event in the window in one pass. Checked-in people are left out (ER23).
- **Clock:** `enqueueReminders(pool, now: Date)` passes `now` as a parameter; `startEmailJobs` gets `clock: () => Date` (default `() => new Date()`). Neither `sender.ts` nor `reminders.ts` reads the real time for the window (ER26).
- **Timer and start-up (ER32-ER38, ER47):** `createRunner` calls the task at start, then with `setInterval(intervalMs)`; a `running` promise guards against overlap (a firing while it is set is skipped); the task is wrapped in `try/catch` and `onError` gets the error message. `stop()` calls `clearInterval` and awaits the running promise. `index.ts` first calls `readIntervalMs(process.env)` and `readMailConfig(process.env)` in a `try/catch` (print the message, `process.exit(1)`), creates the pool with `createPool()`, passes it to `createApp({ pool })` (an existing option), calls `listen`, then `startEmailJobs` with the Resend transport, and registers `SIGINT` and `SIGTERM`: `await jobs.stop()`, `server.close()`, `pool.end()`. The runner is not started in `createApp`, so tests of the app and of the routes never start a timer or need mail settings.
- **Logging:** `log` (default `console.log`) prints `[email] sent <kind> <id>` (ER7); `onError` (default `console.error`) is for failed tries and round errors only. No address, subject, body or key anywhere.
- **Verify at install** (the code-writer does this right after `npm install resend`, before writing ER39-ER43, and notes the result in the session file): (1) in the installed types, where `idempotencyKey` goes (second argument `emails.send(payload, { idempotencyKey })` per the changelog, or inside the payload) and whether the options accept `signal`; (2) that `{ data, error }` has `error.name`, `error.message` and, if present, `statusCode`; (3) that `new Resend('')` throws or not (ER45 makes this unreachable at start). If `signal` is not accepted, ER43 keeps only the timer race, and the spec line "also passes `AbortSignal`" is dropped; nothing else changes.
- **API:** none. No routes are added.

## 6. Open questions

D52 answers 1-5, D56, D58 and D59 are settled and not asked again. Questions that are left (each has a recommendation; if you do not answer, the recommendation is used):

1. **Default `batchSize`.** The spec uses 5 per 10 s tick (ER4), so one sender stays far below Resend's default of 10 requests per second and a burst of reminders does not turn into `429` failures that eat the 3 tries. **Recommended: 5.** The cost is speed (about 0.5 emails per second); 100 reminders take about 3 minutes. If you prefer 20 and accept possible `429` retries, change one default.
2. **`send_error` column.** The spec adds it (ER1, ER11, ER17). **Recommended: keep it**, a short reason of the last failed try (addresses replaced), so an `error_sending` row (for example the free-tier 403) can be understood after the console is gone. If you want the smallest migration, drop the column and ER17's second half; nothing else changes.
3. **Database errors are not tries.** A row whose send hits a database error (not a failed transport call) is not counted as a try (ER17). **Recommended: keep**; only a failed transport call gives up, and the runner reports database errors each round.
