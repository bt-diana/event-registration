# Spec: Change an event's capacity and promote the waiting list (M4, organizer, API only)

Feature spec for the organizer side of milestone M4, made from `SPEC_TEMPLATE.md` (sections 1-5; its behaviours are not requirements). Roadmap step 21 (tests, then code); behaviour B10; `DATABASE.md` 3.9, 3.8, 3.1 and decision 15. It is a **new file**. It adds one route, `POST /events/:id/capacity`. No migration: `events.capacity`, the `promotion` outbox kind and the waitlist index exist (`DATABASE.md` section 1). The web side is `capacity-web.md` (W-CP ids; roadmap steps 22-23). Ids here are **CP1, CP2, ...** (checked: free).

Rules are reused, not copied. The field rule is `events.md` E2 (capacity is a JSON integer from 1 to 100000; E3 adds nothing for a number); the closed-event codes and their order are `email-reminders.md` ER64 (this spec is the "M4 capacity tests" that ER82 points to); ownership is `DATABASE.md` 3.8 (404, one body); the lock is the one of 3.1, 3.6 and 3.7 (`registration.md` section 3); the promotion row and its text are `cancel-registration.md` CR7 (same `promotionEmail`, not a second copy).

**State of the code.** `api/src/events/manage.ts` has `inEventLock` (the transaction and the ownership lock for reschedule and cancel) and `api/src/events/routes.ts` has the two M7 routes. `cancel-registration.md` (CR1-CR27) is specified; `cancelRegistration` and `promotionEmail` may not be built yet when this is built (see section 3, "Shared promotion helper").

## 1. Goals and expected behaviour

**Goal.** A logged-in organizer changes the seat limit of an own event that has not started. Raising it gives the new free seats to the first people on the waiting list, in queue order, each with one `promotion` email row. Lowering it is allowed only down to the number of people already registered; below that the organizer is told how many are registered and nothing changes. The seat count never goes above `capacity`, also when changes, registrations and cancels come at the same moment.

**Route: `POST /events/:id/capacity`** (guard `requireOrganizer`), body `{ "capacity": <integer> }`. Why a POST: it is an action with side effects (promotions and emails), like `POST /events/:id/reschedule` and `POST /events/:id/cancel`; `PATCH /events/:id` refuses `capacity` on purpose (`event-edit.md` EE4). It collides with no route. The organizer is the cookie's, never a body or path value.

**Answer on 200:** the organizer event shape (`OrganizerEvent`: `id`, `title`, `description`, `starts_at`, `ends_at`, `duration_minutes`, `capacity`, `registered`, `seats_left`, `status`, `schedule_version`, `cancelled_at`, `created_at`) built from the committed state, so `registered` and `seats_left` already include the promoted people. It says nothing about who was promoted (open question 7).

**Order of checks** (decided here; the same as ER61-ER64): guard (401/403) -> `:id` is a uuid (else 404, no query) -> body check (400, no query) -> `BEGIN` -> lock query with ownership (no row = 404) -> state under the lock (409: `event_cancelled`, then `event_passed`, then `event_started`) -> count of `registered` rows -> below the count (409 `capacity_below_registered`) -> same value (200 no-op) -> writes -> `COMMIT` -> read. `now` is read once per request in the app (`new Date()`), as the M7 routes do; the state comes from `deriveStatus` and `endsAt` in `api/src/events/status.ts`.

**Behaviours.** Each line is something a test can prove (Vitest; `createApp().listen(0)` and `fetch`; rows by SQL with the helpers in `api/test/db/helpers.ts` and `api/test/auth/helpers.ts`). "Yes" means the test is written and committed before the code (red). ROADMAP lists no tests-first for B10 (`DATABASE.md` 3.9 says "test first: no"); the exception is on purpose: the promotion count and order, the refusal that writes nothing, and the lock races are the only hard parts and decide the shape of the transaction, so they go in the red commit. All other CP tests may be in the same red commit.

**Out of scope.** The capacity form (`capacity-web.md`); changing capacity of a cancelled, ended or running event; editing capacity through `PATCH /events/:id` (refused, `event-edit.md` EE4); changing `starts_at`, duration, title or description; choosing who is promoted (the order is `queue_no`) or promoting from the waiting list by hand; a "seats changed" email to registered or waiting people; an email to the people who stay waiting; undoing a change; a minimum or maximum other than E2's 1 to 100000; capacity per user group; a count of promoted people in the answer (question 7); a new migration, outbox kind or status; changing the sender, the reminder worker or the registration, cancel and check-in services' behaviour (the shared helper of section 3 is a move, with their tests unchanged); live updates.

**Assumptions.** Change any of these first in this file.
- `registered` counts `status = 'registered'` rows, checked-in people included (they hold a seat, E10, AR3).
- A waiting list can only exist while the event is full, so a lowering at or above the registered count has no one to promote in practice (CP7). The uniform rule "promote up to the free seats" (CP9, CP13) also covers states only SQL can make.
- `event_started` is refused as asked by the task and the order of ER64, although `DATABASE.md` 3.9 and 3.10 and ER82 name only `event_cancelled` and `event_passed` (question 2).
- A repeat of the same request is a 200 (CP6), as for reschedule (ER65), cancel (ER76) and register (R4): a double click or a retry is not an error.
- The promoted person gets the ticket code they already have; the promotion text is `cancel-registration.md` CR7 and is not fixed beyond title, start and code.
- The reminder worker reads `registered` rows; a promoted person inside the 24-hour window gets a reminder at the next worker run (CP17). The worker race of `cancel-registration.md` question 4 does not apply: no reminder is deleted here.

No screens in this spec (API only). The screen is `capacity-web.md`. What the API gives it: 200 with the full organizer event (put into the cache as it is; `capacity`, `registered`, `seats_left` are the new numbers); 400 `invalid_input` (a field error; the client checks first); 409 `capacity_below_registered` with `registered` (a field error with the real count); 409 `event_cancelled` / `event_passed` / `event_started` (the control is not offered, or an error line); 404 (not found); 401/403 (re-check `me`). ## 3. Architecture decisions

- **Apps:** `api/` only. Express 5, TypeScript, Vitest, `pg`. No migration, no library, no env variable.
- **Where:** `setCapacity(pool, organizerId, eventId, capacity, now)` in `api/src/events/manage.ts`, next to `rescheduleEvent` and `cancelEvent`, using `inEventLock` (add `capacity` to its `LOCK_SQL` columns and to `LockedEvent`; the other two functions ignore it, their tests stay). The route is in `eventsRouter` (`api/src/events/routes.ts`) next to the two M7 routes: `requireOrganizer`, uuid check, `parseCapacity(body)` (pure; reuses `fields`, `isIntegerIn`, `MIN_CAPACITY`, `MAX_CAPACITY`), result mapping, then the same read as the M7 routes for the 200 (`SELECT_WITH_COUNT ... WHERE e.id = $1 AND e.organizer_id = $2 GROUP BY e.id`, `organizerShape(row, now)`). Do not duplicate the limits.
- **Result union:** `{ kind: "not_found" } | { kind: "refused"; error: "event_cancelled" | "event_passed" | "event_started" } | { kind: "too_low"; registered: number } | { kind: "ok"; eventId: string }`. `ManageResult` may be widened or a second type used; the route maps `too_low` to 409 `{ error: "capacity_below_registered", registered }`.
- **Steps in `setCapacity`** (inside `inEventLock`, after the lock query):
  1. `cancelled` -> `refused` `event_cancelled`; else `startedOrPassed(event, now)` (already in `manage.ts`, ER64 order) -> `refused`.
  2. `SELECT count(*)::int FROM registrations WHERE event_id = $1 AND status = 'registered'`.
  3. `capacity < count` -> `too_low` with the count. `capacity === event.capacity` -> `ok`, no write.
  4. `UPDATE events SET capacity = $2 WHERE id = $1` (nothing else in the `SET`).
  5. `free = capacity - count`; if `free > 0`, call the shared helper `promoteWaiting(client, event, free)`; `ok`.
- **Shared promotion helper.** `promoteWaiting(client, event, limit)` in `api/src/registrations/service.ts`, next to `ticketEmail` (and `promotionEmail`): in one statement, `WITH picked AS (SELECT r.id FROM registrations r WHERE r.event_id = $1 AND r.status = 'waitlisted' ORDER BY r.queue_no LIMIT $2 FOR UPDATE OF r), moved AS (UPDATE registrations r SET status = 'registered' FROM picked WHERE r.id = picked.id RETURNING r.id, r.user_id, r.ticket_code)` then one `INSERT INTO outbox (...) SELECT ..., 'promotion', <locked schedule_version>, <locked starts_at>, u.email, subject, body FROM moved JOIN users u ... ON CONFLICT (registration_id, kind, schedule_version) DO NOTHING` (served by `registrations_waitlist`). It returns the number promoted. The subject and body come from `promotionEmail(event, ticketCode)` of CR7, so build the text per row in the app or with a SQL format that gives the same text; the test of CP12 checks title, start and code. `cancelRegistration` (CR) can call the same helper with `limit` 1 after its capacity check; whichever step is built first creates it, the other reuses it, never two copies. If `cancelRegistration` already has its own inline version, moving it into the helper is a pure refactor with the CR tests unchanged.
- **Concurrency (B10, B4, B3):** the event row lock serialises this change, register, cancel and the M7 writes of one event; different events never block each other. The count, the waiting list and the capacity are read after the lock. The promoted rows are locked by the `UPDATE`; nothing else takes the registration row of a waiting person. `now` is read once per request, in the route, as the M7 routes do (question 6).
- **Emails:** only `promotion` rows, written in the transaction; the sender sends them (ER9). Nothing is sent, printed or logged here.
- **API:**

| Route | Guard | Body | Success | Errors |
|---|---|---|---|---|
| `POST /events/:id/capacity` | `requireOrganizer` | `{ capacity }` integer 1 to 100000 | 200 organizer event (also the no-op) | 400 `invalid_input`, 401 `not_logged_in`, 403 `wrong_role`, 404 `not_found` (malformed, unknown or not yours), 409 `event_cancelled` / `event_passed` / `event_started`, 409 `capacity_below_registered` (+ `registered`) |

## 6. Open questions (each with a recommended answer)

1. **Route.** `POST /events/:id/capacity` or a `capacity` key in `PATCH /events/:id`. **Recommended: the POST** (it has side effects; reschedule and cancel are action POSTs; `event-edit.md` EE4 already refuses `capacity` in PATCH). Alternative: accept it in PATCH, which makes edit depend on promotion code.
2. **Running events (`event_started`).** The task asks for the cancelled, passed and started refusals in the order of ER64. `DATABASE.md` 3.9 and 3.10 and ER82 name only the first two. **Recommended: refuse a started event (CP4)** and add the code to those three places in the build step. Alternative: allow a running event, which helps on the day (more people can be let in), at the price of one fewer refusal and a different edge.
3. **Error code and body for "below the count".** **Recommended: 409 `capacity_below_registered` with a second key `registered`** (it is a conflict with current state, the web needs the number, and it needs no field name). Alternative: 400 `invalid_input` (but the body would still need the count, and a 400 means a bad request, not a state).
4. **Order of "below the count" and "same value".** **Recommended: below first** (CP5 before CP6), so a state SQL made (registered above capacity) is never hidden by a no-op. Alternative: same value first.
5. **Same value.** **Recommended: 200 no-op, nothing written** (CP6), like ER65. Alternative: 200 that still promotes up to the free seats (a repair for states only SQL can make); not needed by the task.
6. **Where `now` is read.** **Recommended: once per request in the route, like the M7 routes.** Alternative: after the lock, as `event-edit.md` does (a request that waited for the lock cannot act on an event that started meanwhile); one more clock argument, little gain.
7. **Count of promoted people in the answer.** **Recommended: no** (the organizer event shape stays exactly as ER86 says; the page shows `registered` and `seats_left`). Alternative: an extra `promoted` key, which changes the key list for this one route.
