# Spec: Attendee emails table (M6 UI) and reschedule / cancel event (M7 UI), web

Feature spec for the web side of milestones M6 and M7, made from `SPEC_TEMPLATE.md` (sections 1-5; its behaviours are not requirements). Roadmap steps 33 (M6 part, W-EM1-W-EM15), 34, and **38 (M7 part, W-EM16-W-EM34, the last section of the behaviours below)**; step 39 builds it, tests first. The API side is `email-reminders.md`: the route `GET /events/:id/registrations/:registrationId/emails` (ER48-ER60, decision D74, session `18-10-2046_email-reminders-web-spec`), the outbox fields (ER1, D56, D58), and for M7 the routes `POST /events/:id/reschedule` and `POST /events/:id/cancel` (ER61-ER87); this file does not change them. **The open questions 10-17 of `email-reminders.md` are still unanswered; this part is built on their recommended answers** (cancel of a cancelled event is 200; a running event gets 409 `event_started`; checked-in people get no email), and says so where it matters. Ids are **W-EM1, W-EM2, ...** (the prefix `W-E` is taken by `events-web.md`).

**What changed (D74).** The earlier version of this file planned two static email lines on the ticket page (a demo note and a reminder line, old W-EM2, W-EM3, W-EM4, W-EM5). None of that was built. It is removed. Instead, the organizer opens a table of the emails of one attendee from a link in the registrations table. All ids below are new; the old W-EM1-W-EM8 no longer exist. **The ticket page gets no email lines any more** (W-EM14).

Style model: `checkin-web.md` (fetch on open and on return, no polling, D50/D51) and `arrivals.md`/`registration-web.md` (organizer screens, guards, states). Login, session, guards and `ApiError` are `auth-web.md`; query helpers are `web/src/events/queries.ts`. Style values are `docs/brand.md`. Nothing is live (D51): no polling, no server-sent events.

## 1. Goals and expected behaviour

**Goal.** In the organizer registrations table (`/registrations`, `registration-web.md` W-R20), each row has a link "View emails". It opens a page with one table: the emails of that one attendee for that event (ticket, promotion, reminder and the others), as the API returns them, newest first, with their status. The page shows just the table and the headings and states around it; no extra text, notes or status explanations. Read only: no button changes anything.

**What the API gives** (`email-reminders.md` ER48-ER60): 200 `{ attendee_name, emails: [ { id, kind, status, to_email, subject, created_at, sent_at, send_attempts, send_error } ] }`, newest first, all rows, no body and no ticket code; 404 `not_found` for an unknown or foreign event or registration; 401; 403.

**Behaviours.** Each line is checked with a component or unit test (`fetch` mocked; fake timers only for the "nothing runs by itself" test). "Test first" ones get the test before the code.

### M7: reschedule and cancel the event (steps 38, 39)

**Goal.** On the organizer view of `/event/:id` (the owner, `events-web.md` W-E10) the organizer can move the event to a new start (a form) and cancel it (a button and a confirm step), while it is still in the future. The public event page and the ticket page show the cancelled state; the new time shows by itself. Each behaviour is checked with a component test (`fetch` mocked; fake system time where the clock matters). "Test first" ones get the test before the code (step 39).

**What the API gives** (`email-reminders.md` ER61-ER87, recommended answers): both routes answer 200 with the organizer event (the `OrganizerEvent` keys, `schedule_version` a number, `status`, `cancelled_at`); 401 `not_logged_in`; 403 `wrong_role`; 404 `not_found` (bad, unknown or foreign id); reschedule only: 400 `invalid_input` (bad body, or `starts_at` not after now); 409 `event_cancelled`, `event_passed` (ended), `event_started` (running). Cancel of an already cancelled event is 200 (ER76). Reschedule to the same instant is 200 with the same `schedule_version` (ER65), and that is how the web tells a no-op. The answer has no error key besides `error`. `PublicEvent`, `PublicListItem`, `Registration` and `MyRegistration` carry **no** `schedule_version` or "rescheduled" field (only `OrganizerEvent` does).

**Out of scope (M7 part).** A "Rescheduled" badge, line or counter on the public pages or the ticket page (needs an API field, question 13); a count of how many times an event was moved; editing title, description, capacity or duration; a calendar picker library; an undo of cancel or "re-open"; choosing which registrations get a cancel email; a preview of the emails; a reason or message field; cancel or reschedule of a running or ended event; the attendee cancelling the own registration and the capacity form (M4 steps 20-21, other specs); bulk cancel; any change in `api/`; polling or live updates (D50, D51); translations; dark theme.

**Out of scope (M6 part).** The email body or a preview; a resend or re-queue button for `Sending failed` rows; filters by kind or status; paging; a table for a whole event or for all attendees; emails of a ticket page or for attendees; counts of sent or failed emails on the registrations page; a column or badge on the registrations table other than the link; explanations of the statuses; delivery, open or bounce status (D57: `sent` only means the provider accepted it); live updates and polling (D50, D51); translations; dark theme; any change in `api/` (the route is `email-reminders.md` ER48-ER60).

**Assumptions.** Change any of these first in this file.
- The route exists before the web step (`email-reminders.md` ER48-ER60 is built and shipped first, with `api/openapi.yaml` updated), as the arrivals route did.
- The organizer routes live under `/registrations*` with the event in the `event` query (`entries.tsx`, `EventSelect.tsx`), not under `/organizer/events/:id/...` (only `/organizer/events/new` exists there). This page follows that, so the example path `/organizer/events/:id/registrations/:registrationId/emails` is not used (question 1).
- `to_email` is the address stored in the outbox row when the email was written, so it can differ from the attendee's email in the registrations table; the page shows it as stored.
- `Failed tries` is `send_attempts` (failed tries only; a `sent` row after two failures shows `2`). The Error column is the short reason of the last failed try, cleared on success (`email-reminders.md` assumptions); it never holds an address or the body.
- Fetching on open and on return, with no polling, is D50/D51; a retrying row changes only after a return or a reload.
- The back link goes to the registrations page of the same event, not to the browser history, so it works after a reload or a pasted link.

*Assumptions of the M7 part*
- The two routes exist before step 39 (steps 36 and 37, with `api/openapi.yaml` updated) and follow ER61-ER87 with the recommended answers of open questions 10-17 of `email-reminders.md`. If the user answers differently: question 11 (cancel of a cancelled event is 409) changes only the last clause of W-EM27; question 12 (running event allowed for reschedule) changes W-EM16 and the `event_started` text of W-EM23.

## 3. Architecture decisions

- **Apps:** `web/` only. No new library, no API change, no proxy change (`/events` is proxied already). One new route in `App.tsx` and one entry in `entries.tsx`.
- **New file `web/src/registrations/emails.ts`:** type `RegistrationEmails` (`{ attendee_name: string; emails: RegistrationEmail[] }`, with the nine item keys of ER50), `getRegistrationEmails(eventId, registrationId)` (`request` from `auth/api.ts`, throws `ApiError(status)` when not ok, like `getArrivals`), the key `registrationEmailsKey(meId, eventId, registrationId)`, the hook `useRegistrationEmails(eventId, registrationId)` (enabled only for a known organizer and valid ids; `authCheckedCall`; `QUERY_OPTIONS`, `staleTime: 0`, `refetchOnMount: "always"`, `refetchOnReconnect: false`), and the pure `emailKindLabel`, `emailStatusLabel`, and `isUuid` (case-insensitive, the same pattern as the API).

## 6. Open questions (each with a recommended answer)

1. **Path of the page.** The request example was `/organizer/events/:id/registrations/:registrationId/emails`. The router has no such pattern (organizer screens are `/registrations`, `/registrations/scan`, with `?event=`). **Recommended: `/registrations/:registrationId/emails?event={id}`** (W-EM2). Alternative: the long organizer path, which needs its own entry and breaks the "event in the query" convention.
2. **Link on every row.** **Recommended: yes**, also for waiting people (their `promotion` row appears when they get a seat). Alternative: only `registered` rows.
3. **Heading with the attendee name.** Depends on the API returning `attendee_name` (`email-reminders.md` question 5). **Recommended: keep**; if the key is dropped, the heading is "Emails" in every state and W-EM13 loses one clause.
4. **Word for `error_sending`.** **Recommended: "Sending failed"** (plain, no claim about delivery). Alternatives: "Failed", "Not sent".
5. **Show "Failed tries" and "Error".** **Recommended: show both** (the user asked for the data the route returns; this is the only place a failed reminder can be understood). Alternative: hide them for `sent` rows with 0 tries; not worth a rule.
6. **Plain text, not badges.** **Recommended: plain text** (no new colour, and the user asked for just the table). Alternative: reuse the existing `Badge` with a tone.
7. **No request for bad ids (W-EM3).** **Recommended: yes**, a cheap check that also keeps `/registrations/me/emails` (id `me`) from calling the API. Alternative: always call and rely on 404.
8. **Build order and the other outbox spec.** The route must exist first. `email-outbox.md` specifies a different, event-wide route (`GET /events/:id/emails`, `registration_id` filter); see `email-reminders.md` question 4. **Recommended: build the route of ER48-ER60 first and let this page use it only.**
9. **Roadmap and README wording.** Steps 33 and 34 and the README line about "two static lines" are now wrong. **Recommended: update them in the build step** (this spec does not edit them).

M7 questions (10-17 of `email-reminders.md` are the API answers this part builds on; the numbers below continue this file's list):

10. **Build on the unanswered API questions.** **Recommended: use the recommended answers** (200 for a second cancel, 409 `event_started` for a running event, no email for checked-in people). The two places that would change are named in the M7 assumptions.
11. **Hide the controls by the browser clock (W-EM16).** A running event is `active` by status, so only `starts_at` vs the browser clock tells it. **Recommended: hide when `starts_at` is not later than the browser clock; the server still answers 409 `event_started`.** Alternative: always show for `active` and rely on the 409 text (a wrong click on a running event, no clock in the UI).
12. **Hidden or disabled when closed.** **Recommended: hidden** (W-EM16; the badge says why). Alternative: disabled buttons with a hint "Only events that have not started can be changed."
13. **"Rescheduled" on the public page and the ticket page.** Not possible with the current API (W-EM31). **Recommended: no badge now**; the new time and the reschedule email tell it. If you want one: a small API change first (add `rescheduled: boolean`, true when `schedule_version > 1`, to `PublicEvent`, the public list item and the ticket/`MyRegistration` read; ER and openapi update), then a badge "Rescheduled" (muted tone) on the public page and the ticket page. That change is not in steps 36-39.
14. **One extra line on the ticket page for a cancelled event (W-EM30).** It breaks the "no event status" rule of W-R38 only for this case. **Recommended: yes**, it is the only place a checked-in person (who stays `registered`) learns the event was cancelled. Alternative: rely on the badge "Cancelled" of the cancelled ticket and add nothing.
15. **Muted line for a cancelled event on the registrations and scan screens (W-EM32).** Without it the table of a cancelled event looks empty ("No one has registered...") or shows only checked-in people. **Recommended: yes.** Alternative: no change on these screens.
16. **Start empty or prefilled.** **Recommended: empty** (as the create form; the same-time case is still handled, W-EM18/W-EM22). Alternative: prefill with the current start.
17. **Distinct 409 texts need the error code (W-EM34).** **Recommended: read `error` in a small subclass `EventActionError`** and keep `ApiError` unchanged. Alternative: one text for every 409 ("This event can no longer be changed.") and no body reading.
18. **Confirm step.** **Recommended: the in-place panel of W-EM24** (testable, styled, no library). Alternative: `window.confirm` (not styled, awkward to test, blocks the page).
19. **"Emails ... are queued" in the success messages.** True (rows are written in the same transaction, ER67, ER75) and no claim of delivery (D57). **Recommended: keep.** Alternative: drop the second sentence.
20. **Cancel button style.** `brand.md` has no danger colour. **Recommended: `button-secondary` for "Cancel event" and `button-primary` for "Yes, cancel event", no red.** Alternative: add a red tone to `brand.md` and the canvas first.
