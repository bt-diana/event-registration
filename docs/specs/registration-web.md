# Spec: Register button, ticket with QR, scan screen and registration lists (web, M3 UI)

Feature spec for the register button, the ticket (with its QR code), the organizer scan screen and the two registration list routes, made from `SPEC_TEMPLATE.md` (sections 1-5). The API side is `registration.md` (R1-R22) and `api/openapi.yaml`; this file does not change them. Login, session, guards and the header are `auth-web.md` (reused as they are: `RequireRole`, `useMe`, `ApiError`, `request`). The event pages are `events-web.md`; this file replaces its "no register button in M2" (W-E17, last sentence) for Open, Full and Already started. Style values are `docs/brand.md`. Roadmap step 17. The QR and scan parts (W-R24 to W-R37) were added later; they are the web side of the check-in idea of M5 (`checkin.md`, `checkin-web.md`, B6) and are marked where they wait for the check-in API.

## 1. Goals and expected behaviour

**Goal.** A logged-in attendee registers for an event from its public page and sees their ticket (code, status, place on the waiting list). Attendees and organizers each get a registrations screen on its own route. The ticket page also shows a QR code of the ticket code, and the organizer has a camera scan screen that reads it for check-in. Nothing here cancels or sends email (M4), and no check-in request can be sent before the check-in API exists (M5).

**API status (nothing is blocked any more).** Every route this file needs exists: `POST /events/{id}/registrations`, `GET /events/{id}/registrations/me` (one event), the attendee list `GET /me/registrations` (`my-registrations.md` MR1-MR15, `MyRegistration` in `openapi.yaml`; question 1, option A, answered), the organizer list `GET /events/{id}/registrations` (`checkin.md`, `OrganizerRegistration`) and `POST /checkin` (`checkIn` in `openapi.yaml`; questions 2 and 10 are answered in `checkin.md`). The web cannot invent data (it remembers nothing; the lists come from the server). So every behaviour below is **buildable now**: some use only the single-event routes (register button, ticket for one event, routing rules), some no API at all (QR, camera, decoding, validation), and the lists use the two list routes. No placeholder screen is kept: `/registrations/me` without `event` is the real list (W-R18).

**Behaviours.** Each line is checked with a component test (`fetch` mocked). "Test first" ones get the test before the code. Ids are W-R1, W-R2, ...

## 3. Architecture decisions

- **Apps:** `web/` only. React 19, Vite, TypeScript, TanStack Query, `react-router`. No new library for W-R1-W-R23; the QR and scan parts use `qr-creator` 1.0.0 (encoder) and `qr-scanner` 1.4.2 (decoder), both by Nimiq, pinned to exact versions in `web/package.json` (question 9, D46). Both bring their own types; `qr-scanner` pulls in `@types/offscreencanvas` as its own dependency. No API change. No proxy change is left to do for the attendee list: `/events`, `/public`, `/checkin` and `/me` are proxied already (the `/me` line came with `my-registrations.md`); no web route may start with `/me`.
- **API client** `web/src/registrations/api.ts`, built on `request` from `auth/api.ts` and the same `body` idea as `events/api.ts`. Type `Registration = { id, event_id, status: "registered" | "waitlisted" | "cancelled", ticket_code, waitlist_position: number | null, checked_in_at: string | null, created_at }` (as `openapi.yaml`). Functions: `getMyRegistration(eventId)` returns the registration or **`null` on 404** (like `fetchMe` with 401), throws `ApiError(status)` otherwise; `register(eventId)` is `POST` with no body and returns the registration (201 and 200 are both `ok`; the status code is not needed by the UI). `listEventRegistrations(eventId)` reads `{ registrations }` of type `OrganizerRegistration` (the `Registration` keys with `status: "registered" | "waitlisted"`, plus `attendee_name`, `attendee_email`) and throws `ApiError(status)` otherwise (404 included, W-R21). `listMyRegistrations()` sends `GET /me/registrations` and reads `{ registrations }` of type `MyRegistration` (the `Registration` keys with the three extra keys `event_title: string`, `event_starts_at: string`, `event_status: "active" | "cancelled" | "passed"`, as `openapi.yaml`); it throws `ApiError(status)` otherwise (a network error is `ApiError(0)`).
- **Hooks** in `web/src/registrations/queries.ts`: `useMyRegistration(eventId, enabled)` (enabled only for an attendee with a known `me`, so no request for others, W-R1/W-R3), `useRegister(eventId)`, `useMyRegistrations()` (enabled only when `me` is a known attendee; 401/403 re-check `me`, W-R41). Keys: `["registration", meId, eventId]`, `["public-event", id]` (existing), `["registrations", meId]` and `["event-registrations", meId, eventId]` (`useEventRegistrations(eventId)`, enabled once `me` is a known organizer and an event is chosen, 401/403 re-check `me`, W-R23). A shared `onApiError` is the one of events-web: 401/403 invalidate `["me"]`.
- **Register flow:** `useMutation`; `onSuccess(registration)`: `setQueryData(["registration", meId, id], registration)`, `invalidateQueries({ queryKey: ["public-event", id], exact: true })` (seats left, `full`), and `invalidateQueries({ queryKey: ["registrations", meId], exact: true })`. `onError`: by `error.status` as W-R9 (409 also invalidates `["public-event", id]`). The button is disabled by `isPending`; no optimistic update (the seat is decided by the server, W-R8).
- **Ticket status:** one pure function `ticketLabel(registration)` returning the heading and detail lines of W-R7, so the event page, the ticket page and the lists share the words. The button choice is one pure function `registerAction(publicEvent, registration)` returning `"none" | "register" | "register-again" | "waitlist"` following the table in section 2 and `publicStatus` (events-web); tests call it directly for every row.
- **Guards and redirects:** a small `RegistrationsEntry` component for `/registrations` and one for `/registrations/me` in `web/src/registrations/entries.tsx`. They reuse `useMe` and the same loading and error states as `MeGate` (export `MeGate` from `auth/guards.tsx`, no behaviour change). `/registrations/me`: attendee shows the screen; logged out `Navigate` to `/login?next=` (path plus search, as `RequireRole`, W-A4); organizer `Navigate to="/registrations" replace`. `/registrations`: organizer shows the screen; attendee `Navigate to="/registrations/me" replace`; logged out `Navigate` to `/organizer/login?next=`. The screens are plain children, so they do not run any query before the guard accepts. `RequireRole` cannot be used as is for `/registrations` because it shows the wrong-account page instead of redirecting (W-A6).
- **Event page integration:** `PublicEventPage` renders `<RegistrationArea event={...} />` after the seats line. The area reads `me` (already loaded by `EventPage`, W-E10), so it adds no `me` call. `PublicEventPage` for an organizer viewer renders the area as nothing (W-R1).
- **Ticket page:** reads `event` with `useSearchParams`. Both queries start together (no waterfall); the result is drawn after both have settled.
- **Styling:** `styles.css` and `brand.md`: the card for the ticket panel (surface, 1px border, radius 12), the code in a larger Public Sans 700 line with letter spacing, badges as in `brand.md`. The ticket and list screens are not in the design canvas yet; section 6 is the input for it. `brand.md` "Not decided yet" gets updated when the canvas is drawn.
- **QR:** `qr.ts` has `drawQr(code, canvas)`, the only import of `qr-creator` (`QrCreator.render(config, canvas)` with the options of W-R24). `QrCode.tsx` renders the `<canvas role="img" aria-label=...>` and calls `drawQr` in an effect when the code changes (the library draws into the given canvas; it does not add an element). `TicketPage` renders it through `showQr(registration, publicEvent)` (pure, in `ticket.ts`, W-R25) in the ticket panel, never `RegistrationArea`.
- **Scanner:** `scanner.ts` has `hasCamera()` and `startScanner(video, onText): () => void` (W-R37) and asks for nothing itself. `ScanScreen` checks the secure context, calls `hasCamera()`, then `navigator.mediaDevices.getUserMedia`, sets `video.srcObject`, hands the video to `startScanner` (qr-scanner's frame loop with its worker, at most 5 reads per second) and keeps the `MediaStream` to stop its tracks (W-R35). Camera errors are mapped by one pure function `cameraState(error | undefined)` in `camera.ts` returning `"denied" | "none" | "insecure" | "other"` (tested for each `DOMException` name, W-R30; a separate file so that mocking `scanner.ts` does not mock it). The screen state is: camera `idle | asking | active | denied | none | insecure | other` and check `idle | pending | result`; a ref set at the first valid code drops every later text until "Scan next" (W-R33). For W-R34: when the answer is a `checked_in` or `already_checked_in` result, the screen remembers (in a ref) whether the camera was `active`, calls the same `release()` as W-R35, sets the camera state back to `idle` and renders neither `CameraArea` nor `ManualForm` while that result is shown (the scanner effect already stops the scanner when `camera` leaves `active`); `scanNext` then calls `startCamera()` if the ref says it was active. `startCamera`'s own `attempt` check covers a leave during the restart. No new state type, no new file, no new library.
- **Check-in call:** `checkIn(ticketCode)` in `registrations/api.ts` sends `POST /checkin` with `{ ticket_code }` and returns a `CheckInResult`, following question 10 and `openapi.yaml`: 200 `{ outcome: "checked_in", ticket_code, event_title, attendee_name, checked_in_at }`; 409 `already_checked_in` `{ outcome: "already_checked_in", ticket_code, attendee_name, checked_in_at }`; 409 `waitlisted`, `registration_cancelled`, `event_cancelled`, 404 `not_found` and 400 `invalid_input` give `{ outcome: <that code>, ticket_code }`; anything else (401, 403, 5xx, another 409 code) throws `ApiError(status)`, a network error `ApiError(0)`. `useCheckIn()` in `queries.ts` is the mutation. `ScanScreen` takes `submitCode` as an optional prop whose default is that mutation; on a thrown 401/403 it re-checks `me` (W-R13). On a 200 (`outcome: "checked_in"`) it invalidates only `["event-arrivals"]` (the counter, `checkin-web.md` W-C11); no list refetch, no redirect, no polling: the organizer stays on `/registrations/scan`, and the list is loaded again when the organizer returns to `/registrations` (W-R20). `vite.config.ts` gets the proxy line `/checkin`.
- **Attendee list screen:** `MyRegistrations.tsx` is rendered by the `/registrations/me` entry when `event` is missing or empty (the entry and its guard are unchanged, W-R15). It uses `useMyRegistrations()` and renders a `ul`; each row uses the shared pieces: `formatDateTime` (W-E19), the status badge texts of `ticketLabel`/the ticket page (add a pure helper `listStatusText(registration)` in `ticket.ts` returning "Registered", "Waiting list: place {n}" or "Cancelled", tested for each status and places 1 and 3) and a pure `eventStatusBadge(event_status)` returning "Event cancelled", "Ended" or `null`. No sorting code, no polling, no new library.
