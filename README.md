# Event Registration

A small service for event registration. An organizer creates an event with a limited number of seats. People register by email, and at the entrance they are checked in with a ticket code. When seats run out, new people go to a waiting list. When someone cancels, the first person on the list gets the seat and an email.

This is my solution for Task 9. I built it together with an AI agent.

**Demo:** https://event-registration-web-rmbi.onrender.com (log in with the accounts in "Demo logins" below).

> **Draft.** Only the database schema, accounts and login (milestone M1), the web login, sign-up and session screens (M1 step 6), the events API (milestone M2: organizer events, the public event page and the public events list, with an optional event description), the event screens in the web app (M2 steps 11 and 12: organizer events list, create form, one event page with the organizer and the public view) the registration API (milestone M3: register, waiting list, my registration, and the list of all my registrations `GET /me/registrations`), the check-in API (M5: `POST /checkin`, the organizer registrations list `GET /events/:id/registrations` and the arrivals route `GET /events/:id/arrivals`; the web does not read the arrivals route yet), the email API (M6: migration `004_outbox_status.sql`, the outbox sender through Resend with 3 tries, the reminder worker and the timer, the organizer email list `GET /events/:id/emails` and the emails of one attendee `GET /events/:id/registrations/:registrationId/emails`, which the web emails page reads), the reschedule and event-cancel API (M7: `POST /events/:id/reschedule`, `POST /events/:id/cancel`) with its web controls (M7 step 39: the reschedule form and "Cancel event" on the organizer event page, the cancelled line on the ticket page, the registrations page and the scan screen) and the registration screens in the web app (M3 step 18: register button, ticket page with its QR code, the attendee list of all my registrations, the organizer registrations list and the check-in scan screen) are built so far. `[TODO]` marks what I fill in during and after the build. ## Features

- **Events:** description, date and time, seat limit.
- **Registration:** by email. Registering again with the same email does not create a second seat. A participant can cancel *(not built yet, M4)*.
- **Waiting list:** when seats run out, new people go to the list. A cancellation gives the seat to the first person on the list, and they get an email *(the list works; cancel and promotion are not built yet, M4)*.
- **Tickets:** every registered person gets a ticket with a code. A ticket can be checked in only once.
- **Check-in screen:** the organizer scans the ticket QR code with the camera, or types the ticket code.
- **Organizer screen:** how many people are registered, on the waiting list, and have arrived. The arrivals counter is read again when the organizer opens the page (not live).
- **Emails:** ticket on registration, seat from the waiting list, one reminder one day before the event, and a notice when the event is rescheduled.

## Tech stack

| Part | Choice |
|---|---|
| Backend | Node.js, TypeScript, Express 5, `pg`, `cookie-parser`, Vitest; `qr-creator` 1.0.0 (same exact version as the web) and `canvas` 3 (node-canvas, native; draws the ticket QR for the emails, D77). On Windows x64 with Node 22 `npm install` takes a prebuilt `canvas` binary; without one for your platform, npm compiles it, which needs Cairo and build tools |
| Frontend | React, Vite, TypeScript, TanStack Query, `react-router` (v7, declarative routes), plain CSS, Vitest; `qr-creator` 1.0.0 (draws the ticket QR) and `qr-scanner` 1.4.2 (reads it from the camera), both by Nimiq, exact versions (D46) |
| Database | PostgreSQL 18 (Windows service, port 5433) |
| Email | Every email is a row in the `outbox` table; a timer sends it through Resend (the `resend` package, D58), at most 3 tries, then `error_sending`. Each email is sent as html and plain text, built from the stored row at send time; ticket, promotion and reminder emails carry the ticket QR as an inline image (D76, D77) |
| Accounts | Attendees and organizers sign up with email and password. Passwords are stored as an `scrypt` hash with a random salt (`node:crypto`). Login is one signed `session` cookie that lasts 7 days; no sessions table |

The backend and the frontend are separate apps. They talk over HTTP. The reasons for these choices are in the decisions in `sessions/`. Email is sent for real through Resend (D58); without a verified domain Resend delivers only to the address of the account owner (see "Environment").

### Prerequisites

- Node.js 22 (the tested version; 20.12 or newer is the minimum, because the API loads `.env` with Node's built-in loader) and npm
- PostgreSQL 18 with the `psql` command, listening on port 5433 (this project runs it as a Windows service, no Docker). Any recent PostgreSQL on another port works if `DATABASE_URL` says so. No extensions are needed
- Free ports: 3000 (API), 5173 (web) and 5433 (database)
- A [Resend](https://resend.com) account with an API key. The API refuses to start without one (see "Environment")

### Set up the database

The migrator creates the tables but not the database itself, so create an empty one first (use your own `postgres` password):

```bash
psql -p 5433 -U postgres -c "CREATE DATABASE events;"
```

The tests use the same server: each test file creates and drops its own throw-away schema inside the database from `DATABASE_URL`, so the `postgres` user (or any user that may create schemas) is needed.

### Set up the environment

Copy `.env.example` to `.env` in the repository root (the API reads it from there; it is git-ignored, never commit it) and fill in:

| Variable | What to put |
|---|---|
| `DATABASE_URL` | `postgres://postgres:<your password>@localhost:5433/events` |
| `COOKIE_SECRET` | At least 32 random characters: `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"` |
| `EMAIL_API_KEY` | Your Resend API key |
| `MAIL_FROM` | `onboarding@resend.dev` (without a verified domain Resend delivers only to your own account address) |

`PORT` (3000) and `EMAIL_JOB_INTERVAL_MS` (10000 in the example) can stay as they are. All variables are described under "Environment" below.

### Run locally

```bash
# 1. PostgreSQL must be running and the database and .env must be ready (above).

# 2. Backend
cd api
npm install
npm run db:migrate   # applies the pending .sql files in api/src/db/migrations/ (001 to 005); "Nothing to apply" on a repeat
npm run dev

# 3. Frontend (in a new terminal)
cd web
npm install
npm run dev
```

Open http://localhost:5173 and log in with a demo account (see "Demo logins"; migration 005 created them).

Starting the API with a real Resend key sends every `pending` outbox row of that database, so use a test database.

The web app calls the API on its own origin. In development the Vite dev server proxies `/auth`, `/events`, `/public`, `/checkin` and `/me` to the API on http://localhost:3000 (`web/vite.config.ts`), so no CORS is needed and `fetch` uses `credentials: "same-origin"`. This proxy exists only in `npm run dev`; a production build must be served from the same origin as the API (for example behind one reverse proxy), or the login cookie and the calls will not work.

### Open the app on a phone

The phone and the PC must be on the same Wi-Fi. Start the API as above, then start the web app so it listens on the network:

```bash
cd web
npm run dev:host        # dev server with live reload, http://<PC address>:5173
# or, for the built app:
npm run build
npm run preview:host    # http://<PC address>:4173
```

Find the PC's Wi-Fi address with `ipconfig` (the IPv4 address of the Wi-Fi adapter, for example `192.168.0.107`) and open `http://<that address>:5173` on the phone. Only the web app needs `--host`: the phone reaches the API through the Vite proxy on the PC.

- **The page does not load (Windows Firewall).** Windows blocks incoming connections to Node.js by default. When the prompt "Windows Defender Firewall has blocked some features of Node.js" appears, tick **Private networks** and click **Allow access**. If you missed the prompt, open PowerShell **as administrator** and run `New-NetFirewallRule -DisplayName "Vite dev 5173" -Direction Inbound -Protocol TCP -LocalPort 5173,4173 -Action Allow -Profile Private` (remove it later with `Remove-NetFirewallRule -DisplayName "Vite dev 5173"`). The Wi-Fi network must also be set to **Private** (Settings, Network & internet, Wi-Fi, your network). Check that the phone is not on mobile data or a guest network.
- **The camera does not start.** Browsers allow the camera only on https or `localhost`, so over `http://<PC address>` the scan screen shows "The camera needs a secure connection (https or localhost). Enter the code below." Typing the code and showing the ticket QR still work. For a camera test on Android Chrome, open `chrome://flags/#unsafe-treat-insecure-origin-as-secure`, add the address, enable it and restart Chrome (testing only). iPhone Safari has no such switch: use an https tunnel or a local certificate (not set up here).

### Deploy on Render

The demo runs on Render: https://event-registration-web-rmbi.onrender.com. The repository root has a `package.json` with `build` and `start` scripts that run the API in `api/`. ## API

Described in [api/openapi.yaml](api/openapi.yaml) (OpenAPI 3.0.3, hand-written). The behaviours are in [docs/specs/auth.md](docs/specs/auth.md), [docs/specs/events.md](docs/specs/events.md), [docs/specs/event-description.md](docs/specs/event-description.md), [docs/specs/events-public-list.md](docs/specs/events-public-list.md) and [docs/specs/registration.md](docs/specs/registration.md), [docs/specs/my-registrations.md](docs/specs/my-registrations.md) (the attendee's own registrations list) and [docs/specs/checkin.md](docs/specs/checkin.md) (M5: check-in and the registrations list) and [docs/specs/arrivals.md](docs/specs/arrivals.md) (M5: the arrivals route) and [docs/specs/email-outbox.md](docs/specs/email-outbox.md) (M6: the emails of an event) and [docs/specs/email-reminders.md](docs/specs/email-reminders.md) (M6: the emails of one attendee, ER48-ER60; M7: reschedule and cancel). All bodies are JSON; errors are `{ "error": "<code>" }`.

| Route | Answer |
|---|---|
| `POST /auth/users/signup`, `POST /auth/organizers/signup` | 201 `{ role, id, email, name }` and the cookie; 400 bad input; 409 email taken |
| `POST /auth/users/login`, `POST /auth/organizers/login` | 200 `{ role, id, email, name }` and the cookie; 400 bad input; 401 wrong email or password (same answer for both) |
| `POST /auth/users/logout`, `POST /auth/organizers/logout` | 204, cookie cleared |
| `GET /auth/me` | 200 `{ role, id, email, name }` for either role (the only "me" route); 401 not logged in |

Seven auth routes. There is no role-specific `GET /auth/users/me` or `GET /auth/organizers/me`; those paths answer 404.

Events (M2, [docs/specs/events.md](docs/specs/events.md)):

| Route | Answer |
|---|---|
| `POST /events` (organizer) | Body `{ title, description, starts_at, duration_minutes, capacity }`; `description` is optional. 201 organizer event; 400 bad input; 401 not logged in; 403 attendee |
| `GET /events` (organizer) | 200 `{ events: [...] }`, only the caller's events, by `starts_at` then `id`, no pagination; 401; 403 |
| `GET /events/:id` (organizer) | 200 organizer event; 404 for an unknown id, an id that is not a uuid, or another organizer's event (same body); 401; 403 |
| `POST /events/:id/reschedule` (organizer) | Body `{ starts_at }` (ISO 8601 with `Z` or an offset, in the future; other fields ignored). 200 organizer event with the new start, `ends_at` and `schedule_version` + 1; the same instant is a no-op (200, nothing written). Queues one `reschedule` email per waiting and not checked-in registered person and deletes pending reminders of older versions. 400 `invalid_input`; 404 (same body as above); 409 `event_cancelled`, `event_passed` or `event_started`; 401; 403 |
| `POST /events/:id/cancel` (organizer) | No body. 200 organizer event with `status` `cancelled` and `cancelled_at`; waiting and not checked-in registered people become `cancelled` and get one `event_cancelled` email each, checked-in people are left as they are, nobody is promoted, pending reminders are deleted. A second cancel answers 200 and writes nothing. 404; 409 `event_passed` or `event_started`; 401; 403 |
| `GET /public/events` (no login) | 200 `{ events: [...] }` with items `{ id, title, starts_at, ends_at, duration_minutes, capacity, status, has_started, seats_left, full }` (no `description`): only events that are not cancelled and not ended, full ones too, by `starts_at` then `id`, at most 100, query string ignored; `{ events: [] }` when none ([docs/specs/events-public-list.md](docs/specs/events-public-list.md)) |
| `GET /public/events/:id` (no login) | 200 `{ id, title, description, starts_at, ends_at, duration_minutes, capacity, status, has_started, seats_left, full }`; 404 unknown or malformed id |

The organizer event is `{ id, title, description, starts_at, ends_at, duration_minutes, capacity, registered, seats_left, status, schedule_version, cancelled_at, created_at }`. `status` is derived when the event is read: `cancelled`, else `passed` once `starts_at + duration_minutes` is reached, else `active` (nothing is stored). On the public page a cancelled or passed event has `seats_left` 0 and `full` false.

The description ([docs/specs/event-description.md](docs/specs/event-description.md)) is plain text. It is trimmed and may have up to 2000 characters (code points) and no NUL; a missing, `null` or blank one is stored as `""`. It is always a string in both shapes, the same for every status, and the API never changes or escapes it. It is set only on create (there is no edit route yet).

Registration (M3, [docs/specs/registration.md](docs/specs/registration.md)):

| Route | Answer |
|---|---|
| `POST /events/:id/registrations` (attendee) | No body (ignored). 201 new registration (`registered` while seats are left, else `waitlisted`); 200 the same registration when the account is already registered or waiting; 409 `event_cancelled` or `event_passed`; 404 unknown or malformed id; 401; 403 organizer |
| `GET /events/:id/registrations/me` (attendee) | 200 the caller's registration in any status (`registered`, `waitlisted` or `cancelled`), also for a cancelled or passed event; 404 unknown or malformed id, or never registered; 401; 403 organizer |
| `GET /me/registrations` (attendee, [docs/specs/my-registrations.md](docs/specs/my-registrations.md)) | 200 `{ registrations: [...] }`: every row of the caller in any status (`registered`, `waitlisted`, `cancelled`; after a cancel and a new registration both rows), also for cancelled and passed events, by the registration's `created_at` newest first, then `id` descending; each item is the registration shape plus `event_title`, `event_starts_at` and `event_status` (`active`, `cancelled` or `passed`, derived per request); `[]` when there are none. The user comes from the cookie only (query string and body ignored); no 400, no 404. 401; 403 organizer. `Cache-Control: no-store`, one statement, no lock, no paging, writes nothing |

The registration is `{ id, event_id, status, ticket_code, waitlist_position, checked_in_at, created_at }`. `ticket_code` is 10 characters from A-Z without I and O, and 2-9; waiting people get one too. `waitlist_position` is the 1-based place on the waiting list, counted when it is read, and `null` unless the status is `waitlisted`. Registering is one transaction that locks the event row (`FOR UPDATE`), so seats are never over-sold. A new seat also stores one `ticket` row in the `outbox` table; the email timer sends it (see "Project status").

Check-in (M5, [docs/specs/checkin.md](docs/specs/checkin.md) and [docs/specs/arrivals.md](docs/specs/arrivals.md); all three routes are built):

| Route | Answer |
|---|---|
| `POST /checkin` (organizer) | Body `{ ticket_code }` (trimmed, upper-cased, then 10 characters of the ticket alphabet; other fields ignored). 200 `{ registration_id, ticket_code, event_id, event_title, attendee_name, checked_in_at }` the first time; 409 `already_checked_in` (with the first `checked_in_at` and `attendee_name`), `waitlisted`, `registration_cancelled` or `event_cancelled` (checked first, also for a ticket already checked in); 404 for an unknown code or another organizer's ticket (same body); 400 `invalid_input` for a bad code (no database query); 401; 403 attendee. Allowed before the start and after the end. One conditional `UPDATE` (no lock, no transaction), so of 5 parallel calls one wins; only `checked_in_at` changes, no email |
| `GET /events/:id/registrations` (organizer) | 200 `{ registrations: [...] }`: the `registered` and `waitlisted` rows of the organizer's own event, by `created_at` then `id`, each with the registration shape plus `attendee_name` and `attendee_email`; `[]` when nobody is registered; also for a cancelled or passed event. 404 for an unknown, malformed or other organizer's event (same body); 401; 403 attendee. `Cache-Control: no-store`, one statement for the rows, no lock, no paging. The arrivals counter has its own route (next row); this list stays for the table |
| `GET /events/:id/arrivals` (organizer) | 200 `{ capacity, registered, arrived }` (three numbers, nothing else) for the organizer's own event: `capacity` as stored (not reduced, not clamped), `registered` the taken seats, `arrived` those of them checked in; waiting and cancelled rows are in neither number; `0` and `0` for an event with nobody; also for a cancelled or passed event. 404 for an unknown, malformed or other organizer's event (same body); 401; 403 attendee. One statement (so `arrived` is never above `registered`), no lock, `Cache-Control: no-store` on 200 and 404, writes nothing |
| `GET /events/:id/emails` (organizer) | 200 `{ emails: [...], truncated }`: the outbox rows of the organizer's own event (every kind and status, also of waiting and cancelled registrations), newest first (`created_at` desc, then `id`), at most 200 (`truncated: true` when more matched). Each item: `id, registration_id, kind, status, send_attempts, send_error, to_email, subject, schedule_version, event_starts_at, created_at, sent_at, attendee_name`; never the body or the ticket code. Optional filters `kind`, `status` and `registration_id` (one attendee; a registration of another event gives the same empty list, not 404). 400 `invalid_kind`, `invalid_status`, `invalid_registration_id` (no query); 404 for an unknown, malformed or other organizer's event (same body); 401; 403 attendee. One statement, `Cache-Control: no-store`, writes nothing |
| `GET /events/:id/registrations/:registrationId/emails` (organizer) | 200 `{ attendee_name, emails: [...] }`: the attendee's current name and every outbox row of that one registration of the organizer's own event (every kind and status, also of a waiting or cancelled registration and of a cancelled or passed event), newest first (`created_at` desc, then `id`), no cap; `emails: []` when there is none. Each item: `id, kind, status, to_email, subject, created_at, sent_at, send_attempts, send_error`; never the body or the ticket code. A query string is ignored. 404 for an unknown, malformed or other organizer's event and for an unknown, malformed or other-event registration (one body, no query for a malformed id); 401; 403 attendee; no 400. One statement, `Cache-Control: no-store` on 200 and 404, writes nothing |

Later routes use the middleware in `api/src/auth/middleware.ts`: `authenticate` puts `req.user` or `req.organizer` on the request, and `requireUser` / `requireOrganizer` answer 401 (no login) or 403 (other role).

## How it works

The hard cases are handled in the database, not in application code.

- **Last seat, two people at once:** registration runs in one transaction that locks the event row first. The second person waits, then sees that the seat is gone and goes to the waiting list.
- **One seat per account:** registering needs a login, so the same email is the same account. Inside the locked transaction an active registration of the account is answered again (200, same ticket); a partial unique index on (event, user) for active rows is the safety net.
- **Cancel and promote:** one locked transaction cancels the seat, promotes the first person on the list (by registration time) and saves the email.
- **Check in once:** one `UPDATE ... WHERE checked_in_at IS NULL` statement. If it changes zero rows, the ticket was already used.
- **One reminder:** a worker runs on a timer and saves a reminder with a unique key per registration and event start time. Two workers, or repeated runs, still give one reminder.
- **Reschedule:** one transaction with the same event lock as registering moves the start, bumps the schedule version, deletes the pending reminders with the old time and saves one email for everyone waiting or registered (not yet checked in). A moved event gets a new reminder for the new time, also when it moves back (A -> B -> A -> B). The reminder worker takes a share lock on the event, so it cannot slip in an old reminder behind a reschedule.
- **Cancel the event:** the same locked transaction marks the event cancelled, cancels the waiting and not checked-in registrations, saves one email for each and deletes the pending reminders. A second cancel does nothing. Registering and check-in on a cancelled event are refused.
